日期：2026-11-16
狀態：設計待確認
比賽日：2026-11-25（三）18:15–20:00

## 目的

羽球社與貿聯辦友誼賽，主辦（孟娜）需要比分輸入系統。第二屆用 Google 表單，第三屆（8/20）用本 repo 的
`tournament.html`（隊長輸分、雙方一致才確認、公開計分板）。這次沿用第三屆的計分頁，但賽制不同：

- 只有兩方（兩家公司），**一家公司一個輸分網址**（共 2 個）＋ 1 個觀賽網址
- 勝負是**比點**：五點三勝，每點三戰兩勝
- 計分是 21 分制，上限 30

另外加一個讓場邊有參與感的**公司應援條**：純炒氣氛，不影響任何結果。

## 範圍

**做**：

1. 計分規則改成「每場比賽各自設定」，友誼賽用 21 分制、第三屆維持 15 分制
2. 每場比賽記錄屬於第幾點、A/B 組別
3. 點數計分板（取代兩隊時沒意義的排名表）
4. 建立友誼賽資料（兩家公司、15 場）
5. 公司應援條
6. 分頁標題跟著賽名
7. 產出兩張輸分 QR code 與觀賽連結
8. 人名到了之後掛上出賽選手（沿用第三屆的 `players_a` / `players_b` 機制）

**不做**：

- 局內即時比分（每得一分更新）：每面場地要專人記分，人力負擔太重
- 勝點預測、MVP 投票、照片牆
- 主頁（`index.html`）賽事倒數換成友誼賽：不在需求內，列為待確認
- 管理介面：補登、改判沿用 Supabase 後台 SQL

**反目標**（技術上能動，但這樣就算失敗）：

- 應援功能出錯連帶讓比分輸入或計分板壞掉
- 第三屆的舊比賽畫面或規則被改變
- 輸分 token 進到 git（本 repo 是公開的，第三屆 A 隊 token 外洩過一次）

## 方案比較

### 計分規則放哪

- **A. 直接把全域規則改成 21 分制**：最少改動；但第三屆舊資料的規則跟著變，下次社內比賽又要改回來
- **B. 比賽層級設定**（採用）：`tournaments.score_rule`，前後端都依那場比賽的規則檢查。舊比賽預設 15 分制，行為不變

### 點次與 A/B 怎麼存

- **A. 放寬 `event` 的 check，直接存「男雙A」**：要動既有 check 與 CSS class，分組要解析字串
- **B. 新增 `point_no` 與 `event_tag` 欄位**（採用）：`event` 不變，舊資料不受影響，分組直接用數字

### 應援條更新頻率（使用者交由我決定，採 B）

- **A. 跟比分一起每 10 秒更新**：最簡單；對面暴衝要等最多 10 秒，拔河感鈍
- **B. 應援數另外每 3 秒更新**（採用）：只抓兩個數字，很輕；場邊感覺不到延遲；跟計分完全分開
- **C. Supabase Realtime 長連線**：真即時，但多一個套件、長連線與免費方案連線上限，當天多一個出事點

### 能不能狂按（使用者確認：純炒氣氛）

採「可以狂按，每 2 秒最多算 10 下」：保留激動時的出口，又不鼓勵整晚低頭猛按，順便擋灌水。
應援數不頒獎、不宣布，所以不做身分辨識。

**已知且接受的風險**（設計者決定）：「每 2 秒 10 下」只在前端裁切，後端只檢查單次 `p_n` ≤ 10。
anon key 公開，有心人可用腳本迴圈灌票。不做後端限流的原因：觀賽 token 全場共用，依 token 限流會把所有觀眾一起卡住；
要依裝置限流就得辨識身分，與「不用登入、按就對了」衝突。最壞後果只是拔河條失真，不影響比分；必要時以 SQL 歸零。

## 設計

### 資料庫（新檔 `docs/tournament/friendly-schema-2026-11-25.sql`，可安全重跑）

1. `tournaments.score_rule text not null default 'to15_cap21'`，check 在 `('to15_cap21','to21_cap30')`
2. `tournament_matches.point_no smallint`（可為 null；舊資料為 null）、
   `tournament_matches.event_tag text not null default ''`，check 在 `('','A','B')`
3. 新表 `tournament_cheers (tournament_id, team_id, count bigint not null default 0, primary key (tournament_id, team_id))`，
   啟用 RLS、不給 anon 任何 policy（只經 RPC）
4. `tournament_public_payload` 多吐 `tournament.scoreRule`、`matches[].pointNo`、`matches[].eventTag`；其餘不動
5. `tournament_report_score` 依 `score_rule` 檢查比分，錯誤訊息依規則顯示（「21 分制、deuce 最高 30 分」）
6. 新 RPC `tournament_cheer(p_token, p_team, p_n)`：`p_token` 可為該比賽的觀賽或任一隊輸分 token；
   `p_n` 必須是 1–10 的整數，否則拒絕；比賽 `finished` 時拒絕；以 upsert 累加；回傳兩隊目前總數
7. 新 RPC `tournament_cheer_totals(p_token)`：回傳 `{ teamId: count }`

上線順序：本檔可先上，舊前端不受影響（payload 只多 key、規則預設 15 分制）。

### 建賽資料（新檔 `docs/tournament/friendly-seed-2026-11-25.sql`）

- **有存在性檢查**：同名同日比賽已存在就不建，可安全重跑
- `club_id`、`created_by` 從第三屆那筆比賽查，不手填
- 比賽：名稱「貿聯×翰林2026羽球聯合友誼賽」、`held_on` 2026-11-25、`status` active、`score_rule` to21_cap30
- 隊伍：先建貿聯、再建翰林（`created_at` 順序決定代表色：貿聯紅、翰林青綠）
- 15 場依上表，team_a 貿聯、team_b 翰林；`event` 填男雙/混雙/女雙、`event_tag` 填 A/B/空、`point_no` 填 1–5
- 檔尾附純查詢取 token；**token 只在 Supabase 查，不寫進任何會 commit 的檔案**

1. `js/tournament-form.js`：規則表 `SCORE_RULES`（每種規則的合法判斷、上限分數、錯誤訊息）；
   `isLegalFinalScore(a, b, rule)`、`validateScores(self, opp, rule)`，`rule` 省略時為 `to15_cap21`（舊行為）。
   輸分彈窗的輸入框上限依規則設定
2. 新純函式模組 `js/team-points.js`：`computeTeamPoints(teams, matches)` 回傳每點的場次比數與拿下方、
   兩隊點數、整體勝方（拿下過半點數即確定）。只計 confirmed 場次；某點已有一方 2 勝後，
   第三場的結果只顯示、不改變該點歸屬。尚無一方取得 2 場確認勝的點，狀態為「進行中」並顯示目前確認比數
   （pending / conflict 場次不計入）；賽程列各場的狀態標籤（比分不一致、等待對方確認…）沿用既有 `matchState`，

## 測試與驗收

### 邊界清單

- 21 分制不合法要擋（前後端都擋）：20:21、21:20、22:21、31:29、30:27、平手、空白、小數、負數
- 21 分制合法要收：21:0、21:19、22:20、29:27、30:28、30:29
- 15 分制（第三屆 30 場已確認比分）以新程式重驗全部合法；既有 jest 全綠
- 某點 2:0 後第三場：可輸入，不改變該點歸屬
- 一方先拿 3 點：顯示確定勝出，後續場次照常輸入
- 雙方比分不一致 → conflict，照舊
- 只能輸入自己公司的場次；錯誤 token；比賽 finished 鎖定輸入與應援
- 應援：`p_n` 為 0、11、負數、小數 → 拒絕；後端關閉時比分功能照常
- 人名未補：只顯示公司名
- 375px 手機版面

### 負載實測

賽前用腳本模擬 50 支手機同時狂按一分鐘（應援送出＋3 秒總數輪詢＋10 秒比分輪詢），
記錄回應時間與錯誤率。在測試比賽上跑，測完刪除。

### 測試資料清理

所有後端實測都在另建的測試比賽上做，測完連同 `report_a` / `report_b` 與應援數一起刪除
（第三屆教訓：單方回報時 status 仍是 pending，只看 status 會漏清）。
