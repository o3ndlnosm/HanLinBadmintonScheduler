# 排場系統主頁 賽事倒數 — 設計 spec

日期：2026-08-04
狀態：已確認，待實作

## 目的

在排場系統主頁（`index.html`）加入 8/20 第三屆運動會的倒數計時，替賽事營造氣氛，
並提供進入比賽計分頁（`tournament.html`）的入口。

社員平常就在用排場系統，主頁是他們最常開的頁面；把倒數放這裡，比放在比賽頁
（賽前沒人會主動去開）更能被看到。

## 範圍

**做**：主頁一塊倒數區域，三個狀態，可點擊跳轉到比賽計分頁。

**不做**：

- 不改 `tournament.html`（比賽頁本身不加倒數）
- 不改後端 SQL / Supabase（主頁不連 Supabase）
- 不做「下一輪開始」倒數（實際比賽會延誤，倒數會變成錯的資訊）
- 不處理裝置時鐘錯誤（見「已知限制」）

## 版位結構

三個狀態共用同一個容器，由上而下固定三層：

```
┌────────────────────────────┐
│ 🏆 第三屆翰林匹克羽球運動會   │  ← 標題（EVENT.name，三狀態不變）
│    16 天 08 : 24 : 31        │  ← 主要文字（隨 phase 變）
│    8/20 (四) 18:10 開打      │  ← 次要文字（由 startAt 推導，during 時不顯示）
│    查看賽程 ›                │  ← 行動呼籲（隨 phase 變）
└────────────────────────────┘
```

## 狀態機

由 `now` 與兩個時間常數決定，三個互斥狀態：

| 狀態 | 條件 | 主要文字 | 次要文字 | 可點 |
|---|---|---|---|---|
| `before` | `now < startAt` | `16 天 08 : 24 : 31` | `8/20 (四) 18:10 開打` | ✅「查看賽程 ›」 |
| `during` | `startAt ≤ now < endAt` | `● 比賽進行中` | — | ✅「進入即時計分板 ›」 |
| `ended` | `now ≥ endAt` | 整塊 `hidden` | — | — |

`before` 狀態下，剩餘時間不足一天時不顯示「天」，只顯示 `08 : 24 : 31`。

## 架構

計算與渲染分離，比照專案既有慣例（`standings.js`、`tournament-form.js` 皆為
純函式 + jest 測試，渲染留在 `tournament.js`）。

### 純函式（可測試核心）

次要文字的日期與星期**一律由 `startAt` 推導，不得寫死**。

2026-08-04 首版曾把「8/20 (三)」寫死在渲染層，而 2026-08-20 實際是星期四——
錯誤同時存在於 spec、plan 與程式碼三處。星期是可以從日期算出來的資訊，
人工維護只會再錯一次；且本設計的目標之一是「下屆比賽只需改 `EVENT` 常數」，
寫死星期與該目標直接矛盾。

推導必須固定用台北時間，不可用裝置本地時區的 `getMonth()` / `getDay()`：
把 epoch 加上 8 小時後改用 `getUTC*` 系列讀取，結果才不受使用者所在時區影響。

```js
countdownState(nowMs, event)
// event: { startAt: string, endAt: string }（ISO 8601 帶時區）
// →
// { phase: 'before', days: 16, hours: 8, minutes: 24, seconds: 31 }
// { phase: 'during' }
// { phase: 'ended' }
```

時間全部由參數傳入。測試不需要碰系統時鐘，也不需要 `jest.useFakeTimers`——
直接餵不同的 `nowMs` 就能覆蓋所有狀態與邊界。

### 渲染層

`initCountdown()` 每秒呼叫 `countdownState()` 一次，只做 DOM 更新：

- `phase` 改變時切換容器的 class 與內容
- `phase === 'ended'` 時設 `hidden` 並 `clearInterval`（不必再跑）
- 分頁隱藏時略過 DOM 更新，`visibilitychange` 回前景時立即更新一次
  （比照 `tournament.js` 的 `pollTick` 作法）

### 常數

```js
const EVENT = {
  name: '第三屆翰林匹克羽球運動會',
  startAt: '2026-08-20T18:10:00+08:00',
  endAt: '2026-08-20T21:00:00+08:00',
  url: 'tournament.html?t=4478488eb60c20146ae9639634944336'
};
```

`startAt` 取自第 1 輪 `timeSlot`（`18:10-18:20`）。`endAt` 不是第 10 輪的預定結束
時間（`19:40-19:50`）：10 輪 × 10 分鐘首尾相接、零緩衝，實際幾乎不可能準時，而主頁
是進入計分頁的唯一入口，19:50 一到入口消失，屆時可能還在打最後幾輪、名次正在決定；
賽後想回看最終戰績的人也找不到連結。故留 70 分鐘延誤緩衝到 `21:00`。`url` 用公開
觀賽 token，本來就要貼社團群組，可公開。

**時區必須寫在字串裡**（`+08:00`）。若寫成 `'2026-08-20 18:10'`，會被當成裝置
本地時間解析——社員手機設在別的時區時，倒數會對到錯的時刻。

## 檔案變更

| 檔案 | 動作 |
|---|---|
| `js/countdown.js` | 新增——純函式 + 渲染 |
| `tests/countdown.test.js` | 新增——純函式測試 |
| `css/style.css` | 加 `.event-countdown` 系列樣式 |
| `index.html` | `.container` 頂部加容器、載入 script |
| `sw.js` | `PRECACHE_URLS` 加 `js/countdown.js`；`CACHE_NAME` v8 → v9 |

### sw.js 必須同時改兩處

`PRECACHE_URLS` 明列每個 JS 檔，新檔案不加進去，離線時載不到。
`CACHE_NAME` 不 bump，既有使用者的 Service Worker 會繼續供舊快取——
stale-while-revalidate 策略下，第一次重整只換到新 SW，第二次才吃到新檔案。

## 視覺

沿用主頁既有語彙，**不引入比賽頁的 F1 深色配色**（兩套配色不相容，`tournament.css`
自成一套 `--f1-*` 變數就是為此）。

- 容器沿用 `.card` 的圓角（`--border-radius: 12px`）與 `--shadow`
- 主色用 `--primary: #4a7dbc` 系
- 位置：`.container` 最頂端、`.court-count-control` 之上——一進主頁就看到，
  但不擋住排場操作
- `during` 狀態的紅點用 CSS `@keyframes` 呼吸效果，不用 JS 驅動

### 兩個實作細節

**等寬數字**：秒數每秒變動會讓整塊寬度跳動，倒數區的數字要
`font-variant-numeric: tabular-nums`。

**用 `<a>` 而非 `div` + `onclick`**：整塊做成 `<a href="tournament.html?t=…">`，
鍵盤 Tab 可達、可中鍵開新分頁，也不需要自己補 `role` / `tabindex` / ARIA。

## 測試

`tests/countdown.test.js` 覆蓋純函式：

- 三個 `phase` 各自回傳正確結果
- 邊界：`now === startAt`（進 `during`）、`now === endAt`（進 `ended`）
- 剩餘時間換算：跨日、剛好整點、剩不到一分鐘
- 不足一天時 `days === 0`

渲染層與實際畫面靠瀏覽器手動驗證（專案既有作法：`script.js` 本體與渲染
不寫自動化測試）。

## 已知限制

倒數依賴裝置時鐘。手機時間設錯的人會看到錯的數字。這是「寫死常數、不連後端」
的固有代價——換成打 API 也只能校正資料、無法校正時鐘，故不另外處理。

## 決策紀錄

| 決策 | 選擇 | 理由 |
|---|---|---|
| 放哪一頁 | `index.html` | 社員平常就開排場系統；比賽頁賽前沒人會去開 |
| 資料來源 | 寫死常數 | 日期已定、QR 已發；主頁維持零外部依賴，不會因 Supabase 睡著而破圖 |
| 賽前可否點 | 可以 | 社員賽前就想確認自己在哪一輪 |
| 賽後處理 | 21:00 才隱藏（非賽程表 19:50） | 10 輪零緩衝的賽程實際幾乎不可能準時，主頁又是進入計分頁的唯一入口；留 70 分鐘延誤緩衝，也讓賽後想回看最終戰績的人仍找得到入口。少一個狀態；下屆比賽改常數即可重啟 |
